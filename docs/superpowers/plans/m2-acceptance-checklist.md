# M2 验收清单（实测结果）

对照设计文档 §2.3 的成功标准逐条验证。**全部在真机上完成**，用 `adb` 驱动 + 截图取证。

设备：Honor BVL-AN16 / Android 16 / Expo Go 57.0.9 / SDK 57
验证方式：`adb shell input tap|swipe` 驱动 + `adb shell screencap` 截图

---

## 成功标准 1：一组做完到记录完成 ≤ 2 次点击

- [x] 进入记录界面后，点「✓ 完成这组」即完成记录（**1 次点击**）
- [x] 点「开始下一组」回到记录态（**1 次点击**）
- [x] 全程无需手动输入数字（数值预填上一组）
- [x] 数值可用**拖动**调整，不必一下下点加减

**证据**：连点「完成这组」→「开始下一组」，组号 1 → 2 → 3 递增；拖 420 物理像素后 22.5 → 45 kg（+9 档，符合 12dp/档的设计值）。

---

## 成功标准 2：记录过程不打断训练节奏

- [x] 训练期间屏幕保持常亮（`keepScreenAwake`）
- [x] 完成一组有轻微震动反馈（`expo-haptics`）
- [x] 组间休息是**正计时**，不催促
- [x] 换动作不必退出记录界面（顶部动作条 + `＋` 弹层）

**证据**：休息界面从 `00:03` 正常起算；动作条可切换「深蹲 / 下斜卧推」，切换后数值按动作正确恢复。

---

## 成功标准 3：训练记录永不丢失 ⭐

- [x] 完成 3 组后强杀 App，重开后「继续上次训练」出现
- [x] 进入后已完成的组数正确
- [x] **息屏挂起后计时仍然准确**

**证据（本轮最关键的验证）**：

| 检查项 | 结果 |
|---|---|
| 完成 2 组后强杀 App → 重开 | 组号正确保留（第 3 组） |
| 息屏前计时 | `18:20` |
| 息屏 35 秒 + 亮屏后 | **`19:01`** |
| Δ 与实测等待时间 | 41 秒 vs 40 秒，**吻合** |

最后一条证明了设计文档 §9 的硬约束：**计时基于 `rest_started_at` 时间戳，不是 `setInterval` 累加计数器**。若用计数器，息屏挂起时它会冻住不动。

- [x] 顶部三个数字：**2 分钟 / 2 总组数 / 320 总容量 kg**
- [x] **卡片第一行是原始次数数组**（`深蹲　8 / 8`）
- [x] 提示文案与次数数组一致

## 真机验证才能发现的问题（单元测试照不到）

这四条全部是**只有真机使用才会暴露**的，且都不在原始计划里：

| # | 问题 | 性质 |
|---|---|---|
| 1 | **换不了动作** —— 一次训练只能练一个动作 | **功能性缺口**，导致 App 无法完成任何一次真实训练 |
| 2 | 隐藏导航栏后顶部动作条压住状态栏 | 安全区遗漏 |
| 3 | 加减按钮调数值太低效 | 交互效率 |
| 4 | 组数只是右上角小灰字，不显眼 | 信息层级 |
| 5 | 完成一组后若一直不按「开始下一组」，`rest_started_at` 会一直留着 —— 重开 App 被堵在休息页，且这段荒唐时长会污染休息数据 | **数据质量 + 可用性** |

第 5 条补了 30 分钟闸门（`domain/rest.ts` + `setRepo.cancelRest` + `store.loadExercises`），并首次给 **store 层**补上集成测试（此前 79 个测试全在 domain/repository，中间那层编排是空白）。
