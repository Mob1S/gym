## 1. 一句话概括

**把界面当成一台测量仪器来设计**：这个 App 的核心信息全是数字（重量、次数、秒数、容量），现在的界面把它们当普通正文处理了。仪表盘的思路是 —— 数字就是界面，其余都是标尺。

本轮**只改视觉与交互工艺，不改任何功能、字段、文案与业务规则**。

---

## 2. 背景：现状诊断

代码质量是好的 —— 分层清晰、注释详尽、198 个单测全绿。**问题纯粹在于视觉层从来没有被设计过。**

### 2.1 五个具体病症

| # | 病症 | 证据 |
|---|---|---|
| 1 | **没有设计系统** | 颜色全是裸字面量，`#2b7fff` / `#8a8f98` / `#eceef2` 在 11 个文件里重复出现 81 次。没有 token、没有主题、没有间距与字号尺度 |
| 2 | **默认模板长相** | `#2b7fff` 蓝 + `#eceef2` 灰药丸 + 白底，就是 Expo 起始模板的调色板 |
| 3 | **零动效与质感** | 没有阴影、没有层次、没有按压反馈。`react-native-reanimated` 已安装却完全没用于界面 |
| 4 | **深色模式是半坏的** | `app.json` 声明了 `userInterfaceStyle: "automatic"`，但每一屏的背景都写死 `#fff` |
| 5 | **数字排版没有工艺** | 只有一个 `RestTimer` 用了 `tabular-nums`。拖动大数字时 `9 → 10` 会让整块数字左右跳一下 |

### 2.2 一个交互冗余（属于本轮范围）

`app/session/[id].tsx` 里 **`DragNumber`（大数字拖动）与 `Stepper`（加减按钮）功能重复** —— 屏幕上下同时摆着两套调值控件，都能改同一个值。这在 5.1 节的「聚焦当前组」设计里是多余的：那一屏的全部意义是拇指不换位置。

> 这正是 brainstorming 里「改动中发现的、影响本次工作的既有问题，顺手一起修」的情形。范围仅限这一个冗余，不做其他重构。

### 2.3 已知代价的消除

2026-09-15 设计文档 §4.3 记着一条代价：**「开发过程中看不到画面，UI 迭代依赖用户在真机上的反馈」**。

本轮把这个瓶颈打掉：用已装的 `react-native-web` 起网页预览，改一版看一版。

## 3. 视觉方向：力量感 · 暗色仪表盘

### 3.1 概念

近黑底 + 高对比强调色 + 超大等宽数字。像杠铃片、像测力计、像健身房里的重器械。健身房灯光下不刺眼，数字一眼可读。

### 3.2 配色：铸铁 + 信号橙

**刻意避开的两条路**：

- `#2b7fff` 蓝 / 紫蓝渐变 —— AI 生成界面的最典型特征
- 荧光绿强调色 —— 试过，但它与健身房的「安全色」语义冲突（绿色 = 安全/通行）

**选定信号橙**：它同时是杠铃片、警示带、力量器械的颜色，语义上就是「力量」。

```ts
// 暗色（基准）
背景  #0B0C0E   近黑，不用纯黑 —— 纯黑在 OLED 上和边框糊在一起
表面  #141619   一级卡片刻度
表面+ #1C1F24   二级 / 按压态
强调  #FF6A1A   信号橙
成功  #32D74B
危险  #FF453A
文字  #F2F4F7 主 / #9BA1AC 次 / #656B76 弱
描边  #2A2E35
```

浅色主题是**同色相映射**，不是简单反色：暖白底 `#FAFAF8` + 同款橙（略深一档保证对比度 `#E4580A`）。

### 3.3 字体：系统优先 + 等宽数字

**不引第三方字体文件**，这是刻意的取舍：

- 中文字体文件动辄 5–10MB，会拖慢启动、带来离线风险
- 换拉丁数字字体则会制造中西混排差异

**改用 `fontVariant: ['tabular-nums']`** —— 数字宽度恒定。这正是现在缺失的关键工艺：拖动 88px 的大数字时 `9 → 10` 不会让整块抖一下。品牌感靠排版、间距、颜色做，不靠字体文件。

字号尺度：`display 88 / h1 34 / h2 24 / title 17 / body 15 / caption 13 / label 11`。

## 4. 实施架构

### 4.1 新增目录

```
src/ui/
  theme.ts          主题色（暗/浅两套）+ useTheme() hook
  tokens.ts         间距 / 字号 / 圆角 / 描边 尺度（与主题无关，两套共用）
  Text.tsx          带排版变体的文字组件
  Screen.tsx        统一外壳：背景色 + 安全区
  Card.tsx          表面卡片
  Button.tsx        主 / 次 / 幽灵 / 危险 四种变体
  Pill.tsx          药丸标签
  StatTile.tsx      统计数字块
  icons.tsx         四个标签栏图标（react-native-svg 手绘描边）
```

### 4.2 分层规则

沿用既有硬性约束：**`app/` 与 `components/` 永远不直接 import `db/`，只能 import `repositories/`**。

`src/ui/` 是纯视觉层 —— 不碰数据库、不碰业务规则、不含状态。它只回答「长什么样」。

### 4.3 主题跟随系统

`useColorScheme()` + 两套 palette。`app.json` 的 `userInterfaceStyle: "automatic"` 保持不变，本轮让代码终于兑现它。

| 屏 | 现状问题 | 改法 |

### 5.1 硬性保留项

以下来自 2026-09-15 设计文档，**本轮一行都不许动**：

1. **次数数组必须原样显示**，并标注「粗略参考」（§8.5）
2. **e1RM 必须始终标注「估算 · 仅供参考」**（§5.4）
3. **「总容量（重量 × 次数）」的措辞**，避免口径混淆（§5.4）
4. **计时用时间戳，不用累加计数器**（§6.2）—— 只改外观，不碰计时逻辑
5. **每完成一组立刻落盘**（§9）—— 不引入任何延迟写库的「优化」
6. 所有既有文案、Alert 措辞、无障碍标签保持原样

### 5.2 记录页的四个状态分支（重做时最容易丢掉的东西）

`app/session/[id].tsx` 有四个早返回分支，视觉重做时**必须逐个保留**，它们的判断条件也不许动：

| 分支 | 触发条件 | 内容 |
|---|---|---|
| 收尾中 | `finishing` | 一帧空白，紧接着跳总结页 |
| 不存在 / 载入中 | `!session \|\| session.id !== id` | 「载入中…」或「这场训练不存在或已结束」+「回主页」 |
| **写保护** | `session.finishedAt !== null` | 「这场训练已经结束」+「回主页」。**结束必须不可逆** —— 深链或系统返回键能绕回这一屏，靠的就是这道判断 |
| 空训练 | `!current`（一个动作都没有） | 「这次训练还没有动作」+「＋ 添加动作」 |

另外还有动作选择弹层（`Modal` + 搜索框 + 按肌群分组 + 空结果文案）与「搜索动作名称」的 placeholder 颜色，都属于本轮范围。

## 6. 动效策略

**不做入场动画。** 健身房场景要的是「立刻可用」，不是「好看地出现」。

只做两处，都有明确目的：

| 动效 | 目的 |
|---|---|
| 数字变档的微反馈 | 已有触觉反馈（`Haptics.selectionAsync`），补一个视觉确认 |
| 休息计时的呼吸点 | 告诉用户「它真的在走」，而不是一个静止的 `00:00` |

两者都尊重系统「减弱动态效果」（`AccessibilityInfo.isReduceMotionEnabled`）。

**实现用 `react-native` 内置的 `Animated`**（`useNativeDriver: true`），不引 `react-native-reanimated` 的动画 API —— 后者在 web 预览下的行为需要额外验证，而这两处动效用内置 API 完全够。

| 决策点 | 选择 | 被否决项与原因 |

| 视觉气质 | 力量感 · 暗色仪表盘 | Clean 精炼白底（白天好看，但健身房灯光下刺眼）；硬核工业粗野排版（个性最强但可读性风险高） |

## 11. 实施记录（as-built）

实施过程中有几处与计划的偏离，以及两个真实踩到的坑，记下来以免下次重犯。

### 11.1 与计划的偏离

| 计划 | 实际 | 原因 |
|---|---|---|
| 从 React Navigation 取标签栏高度 | 自建 `TabBarHeightProvider` | `@react-navigation/bottom-tabs` **并不在依赖里** —— expo-router 把整套 React Navigation 内联在 `build/` 下，只能靠 `expo-router/build/...` 深层路径去够，而那种入口会引到 `.ts` 源码，Metro 未必处理得了。自建十几行 Context 更可控 |
| 首屏用 Card 包「继续训练」 | 同左，但「开始新训练」用 `secondary` 变体 | 主次关系需要靠按钮变体表达，不能只靠排列顺序 |
| 记录页保留 `DragNumber` + `Stepper` 两套控件 | 保留 | 复核后确认二者是**互补**而非重复：拖动适合大跨度（20→60），步进器负责手上有汗时的精确微调。因此把步进器做成次级视觉，不再与拖动控件等权 |

### 11.2 两个真实踩到的坑

**坑一：`exercise_id` 是 `session_exercise_id` 的子串。**
演示执行器最初把「按 `exercise_id` 查」的分支放在「按 `session_exercise_id` 查」之前，
结果是 `listSets` 的查询被前者吃掉，永远返回空数组 —— 表现是记录页拿不到组、
大数字退回兜底值 `20/8`。修法是两条：调换顺序，并且把后者的判断收紧成
**带表别名的 `se.exercise_id`**，从模式上消除歧义。

**坑二：失败的 `pnpm add` 会搬走依赖。**
本机 npm registry 不可达，`pnpm add -D sql.js` 中途失败，把 **40 个包**
（含 `expo`、`react-native`、`expo-sqlite`）重命名进了 `node_modules/.ignored`，
项目当场编译不了。这不是删除，是移动，所以逐一移回即可完全复原
（已复原并复验：typecheck 退出 0、198 个测试全绿）。
**教训：在依赖不可达的环境里，不要用包管理器去试装依赖。**

### 11.3 保留的产物

- **同目录下**的 `dark-record.png` / `dark-history.png`：暗色主题下的实拍截图
  （无头 Chrome + CDP 模拟 `prefers-color-scheme: dark`），作为验收留档。
  它们是**当时那一刻**的留档，不是需要持续维护的资产。

**一个被删掉的中间产物：`metro.config.js`。**
排障途中曾建过一份，只做一件事 —— 把 `.wasm` 加进 Metro 的 `assetExts`，
好让 `expo-sqlite` 的 web 实现能 import 它自己的 `wa-sqlite.wasm`
（Metro 默认名单里没有 `wasm`，不加就解析失败，web 包构建报 500）。

它**在最终的代码路径上已经不起任何作用**：web 端改走内存执行器之后，
`expo-sqlite` 根本不进 web 包（实测 bundle 里连 `wa-sqlite` 字符串都没有），
于是没有任何 `.wasm` 需要被解析。留着一份「修了一个已不存在的问题」的配置，
只会让后来人以为 web 端在用 wasm 版 SQLite。故删除，Metro 回到默认配置。

> 如果将来要让网页预览改用**真** SQLite（而非内存演示数据），这份配置会重新变成必需。
> 届时按 `assetExts` 加 `wasm` 重建即可。

## 12. 追加功能：主题手动切换

本节记录 §9 里那条「不做」被推翻之后的实现。

### 12.1 为什么是三态而不是布尔

用户的原话是「跟随系统 + 手动切换深色/浅色」。听起来像「一个开关 + 一个自动」，
但落到数据上必须是**三态**：

```
system | light | dark
```

布尔（深/浅）表达不了「跟随系统」，而它才是默认值、也是大多数人想要的。
做成布尔就得额外加一个「是否自动」的开关，两个控件互相耦合，比一个三选一更难用。

### 12.2 实现要点

| 关注点 | 做法 | 理由 |
|---|---|---|
| 存哪 | `app_setting` 键值表（**schema v2 新增**） | 设计文档 §6.1 原本就规划了 `app_setting`，但代码里一直没建。这次补上并写成通用键值表，以后加偏好不必再动 schema |
| 迁移 | 追加 `version: 2`，**不动 v1** | v1 早已发布。改 v1 等于让已升到 v1 的真机库永远拿不到这张表（它们的 `schema_version` 已是 1，不会再跑 v1）。这条有专门的回归测试：手工造一个「只跑到 v1」的库，验证它升到 v2 后有表可用 |
| 值校验 | `isThemeMode()` 校验，非法值退回 `system` | 值来自数据库，可能是旧版本写的、手改的、或将来改过语义的。主题读不出来不该让 App 起不来 |
| 分层 | Context 定义在 `src/ui/themeContext.ts`，读库的 Provider 在 `src/store/themePreference.tsx` | `src/ui` 是纯视觉层，不该知道「设置存在数据库里」。它只认 `'light' \| 'dark' \| null` |
| 切换手感 | **先改内存再写库**，写库失败不回滚 | 用户在设置页点一下必须立刻变色。写库失败最多是「重启后回到旧偏好」，比「点了没反应」好得多 |
| 冷启动 | 偏好读出来之前不放行子树 | 否则会先按 `system` 渲染一帧、再整屏换成另一个颜色，每次启动都闪一下 |

**一个测试基础设施的限制被这轮撞到了：** 纯函数 `toThemeOverride` 最初写在
`.tsx` 里，测试直接跑不起来 —— 本项目 jest 的 `testMatch` 只收 `*.test.ts`，
Babel 也只配了 `@babel/preset-typescript`（**没有 JSX 预设**）。
这是既有的、有意的取舍（测试策略见 2026-09-15 设计文档 §10.1：只测纯逻辑）。
所以把那个函数移进 `src/store/themeMode.ts`，而不是去改测试基础设施 ——
纯逻辑留在带 JSX 的文件里等于永远测不到。
