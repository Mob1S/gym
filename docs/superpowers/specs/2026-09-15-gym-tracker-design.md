## 1. 一句话概括

一个 Android 优先、纯本地存储、以「一组一记」为核心的力量训练记录 App；训练结束后，把每个动作各组的次数对比摆出来，配一句**诚实、粗略**的休息提示（练得好时给正反馈）。

---

## 2. 背景与目标

### 2.1 使用者

作者本人（Android 手机），健身房力量训练为主。未来可能分享给朋友，甚至上架，但**不是 v1 的目标**。

### 2.2 要解决的三个问题

1. **记录太啰嗦** —— 健身房里边练边记是负担，很多 App 要点太多下
2. **记不住上次练了什么** —— 不知道该加多少重量，渐进超负荷无从谈起
3. **组间休息全凭感觉** —— 不知道自己实际歇了多久，也不知道歇够了没有

### 2.3 成功标准

| # | 标准 | 怎么验证 |
|---|---|---|
| 1 | 一组做完到记录完成 ≤ 2 次点击 | 真机手测 |
| 2 | 记录过程不打断训练节奏 | 连续用一周不觉得烦 |
| 3 | 训练记录永不丢失 | 训练中强杀 App，重开能恢复 |
| 4 | 训练结束后能看到本次各动作的次数对比，和一句**诚实、粗略**的提示 | 总结页展示原始次数数组，并标注「粗略参考」 |

**第 3 条是一切的底线。** 这个 App 的全部价值就是那份训练记录，丢一次用户就再也不会信任它。

## 3. 范围

### 3.1 v1（第一个可用版本）

- 力量训练记录：训练 → 动作 → 组（重量 × 次数）
- 组间休息**正计时**
- 训练后的组间休息回顾（次数数组 + 粗略提示，含正反馈）
- 历史查看（训练列表 + 单次详情）
- 进步曲线（重量 / 总容量 / 估算 1RM）与个人最好成绩
- 导出 / 导入 JSON 备份

### 3.2 v1.5（用顺手之后再加）

- 训练模板 / 课表
- 有氧记录
- 身体数据（体重、体脂、围度）
- 磅（lb）单位支持
- 热身组标记（v1 所有组一视同仁，均为正式组）

### 3.3 v2 及明确不做

- 饮食热量记录
- 云同步、账号体系
- 小程序
- 社交、排行榜、成就系统

### 3.4 范围决策的理由

- **饮食热量不做**：需要食物数据库和宏量营养计算，工作量可能超过核心记录功能本身，且与「一组一记要快」的定位无关。这是最容易吞掉整个项目的坑。
- **训练模板推迟到 v1.5**：v1 的「沿用上次组数 + 预填上次重量」已经覆盖了大部分便利性，先验证核心记录流程更重要。
- **云同步推迟**：先纯本地把产品用起来，等确认长期在用再加。架构上已留接缝（见 §7.3）。

## 4. 技术选型

**选定：Expo (React Native) + TypeScript**

### 4.1 被否决的方案

| 方案 | 否决理由 |
|---|---|
| **PWA**（网页应用 + 添加到主屏幕） | 锁屏后计时与通知不可靠；未来用 Capacitor 转 APK 时，浏览器沙箱里的 IndexedDB 数据**无法自动迁移**到原生壳；界面仍在 WebView 中渲染，性能上限低 |
| **原生 Android**（Kotlin + Compose） | 开发环境需约 10GB 工具链；iOS 与小程序将来全部重写；编译-安装-查看的反馈循环明显更慢 |
| **Taro / uni-app** | 唯一能同时产出小程序的方案，但 React Native 支持不成熟、手感打折，而小程序只是「将来可能」 |

### 4.2 选 Expo 的理由

1. **一步到位是真 App**，不存在将来「迁移」的返工
2. **原生能力可靠**：后台计时、本地通知、震动、屏幕常亮 —— 这些正是核心需求
3. **开发期用 Expo Go 扫码真机预览**，不需要本地 Android SDK
4. 将来加 iOS 几乎零成本，上架路径顺畅
5. 需要网页版时可用 react-native-web 导出

### 4.3 已知代价（诚实记录）

- **界面渲染在手机上，开发过程中看不到画面**，UI 迭代依赖用户在真机上的反馈
- 出独立 APK 需要 Android SDK（本地构建）或 Expo 云构建（需注册账号）
- 小程序将来仍需重写界面层（这一点 PWA 方案同样无法避免）

### 4.4 依赖清单

| 用途 | 选型 |
|---|---|
| 框架 | Expo (React Native) + TypeScript |
| 本地数据库 | `expo-sqlite` |
| 路由 | `expo-router`（文件即路由） |
| 状态管理 | `zustand`（管理「当前正在进行的训练」与休息计时） |
| 屏幕常亮 | `expo-keep-awake` |
| 震动反馈 | `expo-haptics` |
| 图表 | `react-native-svg` |
| 文件导出与分享 | `expo-file-system` + `expo-sharing` |
| 文件选择（导入） | `expo-document-picker` |
| 单元测试 | `jest` + `jest-expo` |

## 5. 核心交互设计

### 5.1 记录界面：聚焦当前组（方案 B）

屏幕上只呈现**当前这一组**：

```
┌──────────────────────────┐
│ 深蹲            第 3 / 5 组 │
├──────────────────────────┤
│        上次 100 kg × 5    │
│                          │
│     100 kg  ×  5         │  ← 超大字号
│     [−][+]   [−][+]      │  ← 步进按钮
│                          │
│   ┌──────────────────┐   │
│   │   ✓  完成这组     │   │  ← 超大按钮
│   └──────────────────┘   │
├──────────────────────────┤
│        结束训练           │
└──────────────────────────┘
```

**设计要点**

- 拇指永远停在同一个位置，不需要瞄准
- 新的一组**预填上次该组的数值**，多数情况直接点确认
- 动作名下方常驻显示**上次这个动作的成绩**（渐进超负荷最需要的信息）
- 「第 N / M 组」中的 M 默认沿用上次该动作的组数，可随时「+ 加一组」
- 点「✓ 完成这组」时给一次**轻微震动反馈**，让用户不用盯着屏幕确认
- 记录全程屏幕保持常亮

**被否决的两种布局**

| 布局 | 否决理由 |
|---|---|
| A. 全览列表（所有组摊开，点行内 ✓） | 点击目标小；单手够不到顶部；改数值需跳转 |
| C. 列表 + 底部常驻操作条 | 屏幕空间紧张，相比 B 的收益不足以抵消复杂度 |

### 5.2 组间休息：正计时，不是倒计时

这是用户明确要求的设计，也是本 App 与常见健身 App 的重要区别。

```
深蹲 第 3 组 ✓ 已完成
┌──────────────────────────┐
│        组间休息           │
│        01:23             │  ← 往上走，不催
│   刚刚完成 100 kg × 5     │
│  ┌────────────────────┐  │
│  │    开始第 4 组      │  │
│  └────────────────────┘  │
│      或 换下一个动作       │
└──────────────────────────┘
```

**流程**

1. 点「✓ 完成这组」→ 记录该组完成，**立刻开始正计时**，同时记录 `rest_started_at` 时间戳
2. 点「开始第 4 组」→ 计时停止，把这段休息时长写入**第 3 组**的 `rest_seconds`
3. 显示第 4 组的输入界面（预填上次数值）
4. 点「换下一个动作」→ 同样结束计时，这段休息计入上一个动作的最后一组

**为什么是正计时**：不打断训练节奏。用户休息多久就记多久，数据是**观察**出来的，不是**规定**出来的。每一次休息都成为一条可分析的数据。

### 5.3 训练总结页

```
训练完成                腿部日
┌────┬────┬──────────┐
│ 52 │ 18 │  8,240   │
│分钟 │总组数│ 总容量 kg │
└────┴────┴──────────┘
组间休息回顾（粗略参考）
┌──────────────────────────┐
│ 深蹲           5/5/5/3/3  │
│ ⚠ 末组 5 → 3，下次这个动作│
│   可以多歇 30 秒          │
├──────────────────────────┤
│ 腿举          10/10/10/10 │
│ ✅ 全程稳住了，节奏合适    │
├──────────────────────────┤
│ 弯举           12/12/11/9 │
│ ⚠ 多歇 30 秒试试；如果还是│
│   掉，可能是重量偏大       │
└──────────────────────────┘
        [ 保存这次训练 ]
```

**硬性要求：必须把次数数组原样显示出来，并标注「粗略参考」。** 只给结论不给原始数字，用户无法核对，也不会相信。这是本功能的核心设计约束。

### 5.4 指标定义（全文档统一口径）

下面两个指标，在文档、代码、界面里**只能有这一个定义**。

#### 总容量 —— 这是「口径」问题，不是「精度」问题

```
总容量 = Σ (weight × reps)
        取该次训练中所有 is_completed = 1 的组，单位 kg
```

**必须说清楚：这是一种口径选择，不是唯一正确的算法。** 文献里 "volume"（训练量）一词的用法并不统一 —— 有人指总次数，有人指「组数 × 次数」，有人指包含重量的 **volume load**。本 App 采用的是最后一种。

因此：

- 文档与代码中一律使用准确说法 **「容量负荷 / volume load」**
- 界面上标注为「总容量（重量 × 次数）」，避免与其他口径混淆
- 不与采用其他口径的 App 或研究数据做横向比较

#### 估算 1RM（e1RM）—— 这是「估算」问题，必须标注误差与适用范围

**它是估算值，不是实测值。界面上必须始终标注「估算 · 仅供参考」。**

采用三种经典公式的**算术平均**，以降低单一公式的偏差（同一组数据，三个公式会给出不同结果，没有任何一个被公认最准）：

| 公式 | 表达式 |
|---|---|
| Epley | `w × (1 + r / 30)` |
| Brzycki | `w × (36 / (37 − r))` |
| Lombardi | `w × r ^ 0.10` |

```
e1RM = (Epley + Brzycki + Lombardi) ÷ 3
```

**适用范围与限制**（必须同时出现在界面的说明文字里）：

- **只在 `2 ≤ r ≤ 10` 时计算**；`r = 1` 时直接返回 `w`；**`r > 10` 时不显示 e1RM**（外推严重失真）
- 各公式结果互不相同；取平均是为了减少单一公式的偏差，**不代表更准**
- 不反映个体差异（肌纤维类型、训练年限、动作熟练度）
- 公式假设该组接近力竭，留有余力会低估
- 睡眠、饮食、疲劳、压力会让真实极限在日常波动 5–10%
- 复合动作（深蹲 / 卧推 / 硬拉）比孤立动作可靠

**公式一旦确定，不得中途更改** —— 换了公式，「进步」页的历史曲线会出现无解释的断层。将来若必须更换，需在曲线上标注断点。

> 参考：[1RM 公式与限制说明](https://gethealthycalculators.com/one-rep-max-calculator/)（二手来源；三个公式本身是教科书通用内容）

## 6. 数据模型

### 6.1 表结构

```sql
-- 动作库
CREATE TABLE exercise (
  id            TEXT PRIMARY KEY,           -- uuid
  name          TEXT NOT NULL,
  muscle_group  TEXT,                       -- 胸/背/腿/肩/手臂/核心
  equipment     TEXT,                       -- 杠铃/哑铃/器械/自重
  is_custom     INTEGER NOT NULL DEFAULT 0,
  is_archived   INTEGER NOT NULL DEFAULT 0,
  created_at    INTEGER NOT NULL
);

-- 一次训练
CREATE TABLE session (
  id          TEXT PRIMARY KEY,
  name        TEXT,                         -- 如「腿部日」，可空
  started_at  INTEGER NOT NULL,
  finished_at INTEGER,                      -- NULL = 进行中
  note        TEXT
);

-- 训练中的一个动作条目
CREATE TABLE session_exercise (
  id                  TEXT PRIMARY KEY,
  session_id          TEXT NOT NULL REFERENCES session(id) ON DELETE CASCADE,
  exercise_id         TEXT NOT NULL REFERENCES exercise(id),
  position            INTEGER NOT NULL,     -- 在本次训练中的顺序
  note                TEXT
);

-- 一组（核心表）
CREATE TABLE set_entry (
  id                  TEXT PRIMARY KEY,
  session_exercise_id TEXT NOT NULL REFERENCES session_exercise(id) ON DELETE CASCADE,
  position            INTEGER NOT NULL,     -- 第几组
  weight              REAL NOT NULL,        -- kg
  reps                INTEGER NOT NULL,
  is_completed        INTEGER NOT NULL DEFAULT 0,
  rest_seconds        INTEGER,              -- 本组做完后休息了多久（NULL = 未记录/最后一组）
  rest_started_at     INTEGER,              -- 休息开始时间戳；崩溃恢复的依据
  completed_at        INTEGER
);

-- 设置（键值对）与 schema 版本
CREATE TABLE app_setting (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
```

### 6.2 关键字段说明

- **`rest_seconds` 存在「本组做完之后」那一段休息上**。第 3 组做完、第 4 组开始前的休息，存在第 3 组上。这样「开始下一组」这个动作只需写一条记录。
- **`rest_started_at` 是崩溃恢复的关键**。如果 App 在休息期间被杀，重开时用「当前时间 − rest_started_at」仍能算出真实休息时长。
- **计时用时间戳，不用计数器**。哪怕 App 被系统挂起十分钟，算出来的休息时长依然准确。这是不可妥协的实现约束。

### 6.3 关系

```
session ──< session_exercise ──< set_entry
                   │
                   └──> exercise（动作库）
```


## 8. 组间休息提示（训练后）

### 8.1 定位：粗略参考，不是科学结论

**明确不做的事**：不建统计模型、不做跨训练推断、不声称能算出「你的最佳休息时长」。

理由：该领域 2024 年的系统综述与 meta 分析明确指出，组间休息的最优值**至今没有共识**，并且**同一个人在不同训练日的反应存在明显差异**（见 [Rev Bras Med Esporte 2024](https://www.scielo.br/j/rbme/a/Y9vYkwhHhbzKcKNSG9Ft85s/?format=html&lang=en&ilang=en)）。任何声称能算出精确数值的算法都是过度承诺。

所以本功能只做一件事：**把这次训练里这个动作每组的次数摆出来，配一句粗略的话。**

界面上必须标注为「粗略参考」。

> 附：ACSM 立场声明给出的一般参考区间是——多关节动作 2–3 分钟，单关节动作 1–2 分钟。v1 **不基于它做任何自动计算**，仅在设置页作为静态说明文字展示。

### 8.2 输入

**仅限本次训练内的一个动作**，不跨训练比较：

- `reps[]` —— 该动作已完成组的次数，按 `position` 排序
- `rest[]` —— 各组的组后休息时长，可为空

### 8.3 计算

| 量 | 定义 |
|---|---|
| `first` | `reps[]` 的第一项 |
| `last` | `reps[]` 的最后一项 |
| `drop` | `first − last` |
| `avg_rest` | `rest[]` 中非空值的算术平均；全部为空时为 `null` |

**前置条件**：该动作已完成组数 ≥ 3，否则不输出任何提示（数据不足，明确沉默）。

### 8.4 输出分支

| 条件 | 类型 | 文案示例 |
|---|---|---|
| `drop ≤ 0` 且（`avg_rest ≤ 180s` 或 `null`） | ✅ **正反馈** | 「5 / 5 / 5 / 5 全程稳住了，节奏合适」 |
| `drop ≤ 0` 且 `avg_rest > 180s` | 💡 **加重提示** | 「全程 5 次稳定，平均歇了 3 分 20 秒 —— 还有余力，可以考虑加重量」 |
| `drop = 1` | ⚠️ 轻微提醒 | 「末组 5 → 4，下次这个动作可以多歇 15 秒」 |
| `drop = 2` | ⚠️ 提醒延长 | 「末组 5 → 3，下次可以多歇 30 秒」 |
| `drop ≥ 3` | ⚠️ 提醒延长 + 归因提示 | 「末组 5 → 2，多歇 30 秒试试；如果还是掉，可能是重量偏大」 |

**关于「缩短休息」**：原设计中有这一条，现已替换为 `drop ≤ 0` 且休息偏长时的**加重提示**。理由：全程稳定却歇很久，真正的信号是「还有余力」，该加重量——缩短休息只是副作用，不是目标。

### 8.5 强制要求

1. **必须把次数数组原样显示出来**（如「5 / 5 / 5 / 3 / 3」），让用户能自己核对，不能只给一句结论
2. **必须标注「粗略参考」**，不得表述为科学建议或个性化处方
3. 建议增量为固定的两档（15 秒 / 30 秒），**不做百分比计算**，不输出「最佳休息时长」这类精确数字
4. 该动作已完成组数 < 3 时不给提示
5. **不做跨训练推断** —— 每次训练独立判断，不累积、不建模

### 8.6 生效方式（v1）

- 提示**只做展示，不做强制**，不阻断任何操作
- 只在**训练总结页**出现，不在训练过程中弹出
- **不做「到点提醒」，不做「永久忽略」** —— 用户自己决定听不听

## 9. 可靠性与错误处理

| 风险 | 对策 |
|---|---|
| 训练中被系统杀进程 / 手机没电 | **每完成一组立刻写数据库**，不等训练结束。重开 App 自动回到未结束的训练 |
| 锁屏 / 切后台导致计时不准 | 计时基于 `rest_started_at` **时间戳**，用 `now − start` 计算，不依赖 `setInterval` 累加 |
| 数据库版本升级出错 | 版本化迁移，启动时自检，失败则回滚并保留原库 |
| 导入的备份文件损坏 | **先完整校验再写入**，校验不通过就拒绝，绝不破坏已有数据 |
| 导出失败 | 明确告知失败原因，不静默吞掉 |
| 训练中误触「结束训练」 | 二次确认；已记录的数据无论如何都保留 |

## 10. 测试策略

### 10.1 单元测试（重点）

针对 `src/domain/` 中的纯逻辑，这些是「算错了也不会立刻被发现」的地方：

- 容量计算（重量 × 次数求和）
- **e1RM 估算** —— 三个边界必须测：`r = 1`、`r = 10`、`r = 11`（必须不显示 e1RM）；公式须与 §5.4 完全一致
- **容量负荷** —— 只累加 `is_completed = 1` 的组
- **组间休息提示规则** —— 各分支（正反馈 / 加重提示 / 掉次数三档）、组数 < 3 时沉默、休息全空、数组仅 3 项的边界
- 导入 JSON 的校验逻辑：缺字段、类型错误、未来版本号、损坏文件

### 10.2 集成测试

数据库层用内存 SQLite 验证增删改查、级联删除、迁移。

### 10.3 手动测试

界面与真机手感由用户在手机上验证。开发过程中界面画面不可见，这是本技术方案的已知代价（见 §4.3）。

## 13. 附：本次设计中被否决的关键决策记录

| 决策点 | 选择 | 被否决项与原因 |
|---|---|---|
| 技术栈 | Expo / React Native | PWA 计时不可靠且迁移会丢数据；原生 Android 环境成本过高 |
| 数据存储 | 纯本地 + 留同步接缝 | 直接上云同步会让工作量翻倍，且尚未验证产品价值 |
| 记录界面 | 聚焦当前组（B） | 全览列表点击目标小；列表 + 操作条空间紧张 |
| 休息计时 | **正计时** | 倒计时会催促用户，且数据是"规定"出来的而非"观察"出来的 |
| 训练后反馈 | **本次训练内简单对比次数数组** | 跨训练统计推断已被否决：文献本身对最优休息时长无共识，且同一个人不同训练日反应差异明显；RPE 手动评分与「越快越好」冲突，实际会被荒废 |
| 反馈的语气 | **必须包含正反馈分支** | 只挑毛病、从不肯定，用两周就会被无视 |
| 训练指标的呈现 | **区分「口径」与「估算」，都标注适用范围** | 把估算值当实测值展示；把某一种 volume 口径当成唯一定义；1RM 用单一公式却不说它只是几个公式之一 |
| 饮食热量 | 不做 | 会吞掉整个项目 |
| 训练模板 | 推迟到 v1.5 | v1 的"沿用上次组数 + 预填上次重量"已覆盖大部分便利性 |
