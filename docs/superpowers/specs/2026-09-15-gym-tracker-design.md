## 1. 一句话概括

一个 Android 优先、纯本地存储、以「一组一记」为核心的力量训练记录 App；训练结束后，依据实际记录的组间休息数据，给出**带证据、可解释**的休息时长建议。

---

## 2. 背景与目标

### 2.1 使用者

作者本人（Android 手机），健身房力量训练为主。未来可能分享给朋友，甚至上架，但**不是 v1 的目标**。

### 2.2 要解决的三个问题

1. **记录太啰嗦** —— 健身房里边练边记是负担，很多 App 要点太多下
2. **记不住上次练了什么** —— 不知道该加多少重量，渐进超负荷无从谈起
3. **组间休息全凭感觉** —— 不知道自己实际歇了多久，也不知道歇够了没有

### 2.3 成功标准

| # | 标准 | 怎么验证 |
|---|---|---|
| 1 | 一组做完到记录完成 ≤ 2 次点击 | 真机手测 |
| 2 | 记录过程不打断训练节奏 | 连续用一周不觉得烦 |
| 3 | 训练记录永不丢失 | 训练中强杀 App，重开能恢复 |
| 4 | 训练结束能拿到具体的休息建议，且理由清楚 | 总结页每条建议都有证据数字 |

**第 3 条是一切的底线。** 这个 App 的全部价值就是那份训练记录，丢一次用户就再也不会信任它。

## 3. 范围

### 3.1 v1（第一个可用版本）

- 力量训练记录：训练 → 动作 → 组（重量 × 次数）
- 组间休息**正计时**
- 历史查看（训练列表 + 单次详情）
- 进步曲线（重量 / 总容量 / 估算 1RM）与个人最好成绩
- 导出 / 导入 JSON 备份

### 3.2 v1.5（用顺手之后再加）

- 训练模板 / 课表
- 有氧记录
- 身体数据（体重、体脂、围度）
- 磅（lb）单位支持
- 热身组标记（v1 所有组一视同仁，均为正式组）

### 3.3 v2 及明确不做

- 饮食热量记录
- 云同步、账号体系
- 小程序
- 社交、排行榜、成就系统

### 3.4 范围决策的理由

- **饮食热量不做**：需要食物数据库和宏量营养计算，工作量可能超过核心记录功能本身，且与「一组一记要快」的定位无关。这是最容易吞掉整个项目的坑。
- **训练模板推迟到 v1.5**：v1 的「沿用上次组数 + 预填上次重量」已经覆盖了大部分便利性，先验证核心记录流程更重要。
- **云同步推迟**：先纯本地把产品用起来，等确认长期在用再加。架构上已留接缝（见 §7.3）。

## 4. 技术选型

**选定：Expo (React Native) + TypeScript**

### 4.1 被否决的方案

| 方案 | 否决理由 |
|---|---|
| **PWA**（网页应用 + 添加到主屏幕） | 锁屏后计时与通知不可靠；未来用 Capacitor 转 APK 时，浏览器沙箱里的 IndexedDB 数据**无法自动迁移**到原生壳；界面仍在 WebView 中渲染，性能上限低 |
| **原生 Android**（Kotlin + Compose） | 开发环境需约 10GB 工具链；iOS 与小程序将来全部重写；编译-安装-查看的反馈循环明显更慢 |
| **Taro / uni-app** | 唯一能同时产出小程序的方案，但 React Native 支持不成熟、手感打折，而小程序只是「将来可能」 |

### 4.2 选 Expo 的理由

1. **一步到位是真 App**，不存在将来「迁移」的返工
2. **原生能力可靠**：后台计时、本地通知、震动、屏幕常亮 —— 这些正是核心需求
3. **开发期用 Expo Go 扫码真机预览**，不需要本地 Android SDK
4. 将来加 iOS 几乎零成本，上架路径顺畅
5. 需要网页版时可用 react-native-web 导出

### 4.3 已知代价（诚实记录）

- **界面渲染在手机上，开发过程中看不到画面**，UI 迭代依赖用户在真机上的反馈
- 出独立 APK 需要 Android SDK（本地构建）或 Expo 云构建（需注册账号）
- 小程序将来仍需重写界面层（这一点 PWA 方案同样无法避免）

### 4.4 依赖清单

| 用途 | 选型 |
|---|---|
| 框架 | Expo (React Native) + TypeScript |
| 本地数据库 | `expo-sqlite` |
| 路由 | `expo-router`（文件即路由） |
| 状态管理 | `zustand`（管理「当前正在进行的训练」与休息计时） |
| 屏幕常亮 | `expo-keep-awake` |
| 震动反馈 | `expo-haptics` |
| 图表 | `react-native-svg` |
| 文件导出与分享 | `expo-file-system` + `expo-sharing` |
| 文件选择（导入） | `expo-document-picker` |
| 单元测试 | `jest` + `jest-expo` |

## 5. 核心交互设计

### 5.1 记录界面：聚焦当前组（方案 B）

屏幕上只呈现**当前这一组**：

```
┌──────────────────────────┐
│ 深蹲            第 3 / 5 组 │
├──────────────────────────┤
│        上次 100 kg × 5    │
│                          │
│     100 kg  ×  5         │  ← 超大字号
│     [−][+]   [−][+]      │  ← 步进按钮
│                          │
│   ┌──────────────────┐   │
│   │   ✓  完成这组     │   │  ← 超大按钮
│   └──────────────────┘   │
├──────────────────────────┤
│        结束训练           │
└──────────────────────────┘
```

**设计要点**

- 拇指永远停在同一个位置，不需要瞄准
- 新的一组**预填上次该组的数值**，多数情况直接点确认
- 动作名下方常驻显示**上次这个动作的成绩**（渐进超负荷最需要的信息）
- 「第 N / M 组」中的 M 默认沿用上次该动作的组数，可随时「+ 加一组」
- 点「✓ 完成这组」时给一次**轻微震动反馈**，让用户不用盯着屏幕确认
- 记录全程屏幕保持常亮

**被否决的两种布局**

| 布局 | 否决理由 |
|---|---|
| A. 全览列表（所有组摊开，点行内 ✓） | 点击目标小；单手够不到顶部；改数值需跳转 |
| C. 列表 + 底部常驻操作条 | 屏幕空间紧张，相比 B 的收益不足以抵消复杂度 |

### 5.2 组间休息：正计时，不是倒计时

这是用户明确要求的设计，也是本 App 与常见健身 App 的重要区别。

```
深蹲 第 3 组 ✓ 已完成
┌──────────────────────────┐
│        组间休息           │
│        01:23             │  ← 往上走，不催
│   刚刚完成 100 kg × 5     │
│  ┌────────────────────┐  │
│  │    开始第 4 组      │  │
│  └────────────────────┘  │
│      或 换下一个动作       │
└──────────────────────────┘
```

**流程**

1. 点「✓ 完成这组」→ 记录该组完成，**立刻开始正计时**，同时记录 `rest_started_at` 时间戳
2. 点「开始第 4 组」→ 计时停止，把这段休息时长写入**第 3 组**的 `rest_seconds`
3. 显示第 4 组的输入界面（预填上次数值）
4. 点「换下一个动作」→ 同样结束计时，这段休息计入上一个动作的最后一组

**为什么是正计时**：不打断训练节奏。用户休息多久就记多久，数据是**观察**出来的，不是**规定**出来的。每一次休息都成为一条可分析的数据。

### 5.3 训练总结页

```
训练完成                腿部日
┌────┬────┬──────────┐
│ 52 │ 18 │  8,240   │
│分钟 │总组数│ 总容量 kg │
└────┴────┴──────────┘
组间休息建议
┌─────────────────────────┐
│ 深蹲            96s → 120s│
│ 末两组次数 5 → 3，休息偏短 │
├─────────────────────────┤
│ 罗马尼亚硬拉    88s → 100s│
│ 末组重量下滑 10kg         │
├─────────────────────────┤
│ 腿举            74s 保持  │
│ 全程 10 次稳定，节奏合适   │
└─────────────────────────┘
        [ 保存这次训练 ]
```

**硬性要求：每条建议必须附带触发它的证据数字。** 没有理由的建议用户不会信，用两次就会无视。这是本功能的核心设计约束。

**指标定义**（全文档统一口径）：

- **总容量** = 该次训练中所有 `is_completed = 1` 的组的 `weight × reps` 之和，单位 kg。跨动作求和即为整场训练的总容量。
- **估算 1RM** = `weight × (1 + reps / 30)`（Epley 公式），仅用于趋势展示，不宣称是真实极限。

## 6. 数据模型

### 6.1 表结构

```sql
-- 动作库
CREATE TABLE exercise (
  id            TEXT PRIMARY KEY,           -- uuid
  name          TEXT NOT NULL,
  muscle_group  TEXT,                       -- 胸/背/腿/肩/手臂/核心
  equipment     TEXT,                       -- 杠铃/哑铃/器械/自重
  is_custom     INTEGER NOT NULL DEFAULT 0,
  is_archived   INTEGER NOT NULL DEFAULT 0,
  created_at    INTEGER NOT NULL
);

-- 一次训练
CREATE TABLE session (
  id          TEXT PRIMARY KEY,
  name        TEXT,                         -- 如「腿部日」，可空
  started_at  INTEGER NOT NULL,
  finished_at INTEGER,                      -- NULL = 进行中
  note        TEXT
);

-- 训练中的一个动作条目
CREATE TABLE session_exercise (
  id                  TEXT PRIMARY KEY,
  session_id          TEXT NOT NULL REFERENCES session(id) ON DELETE CASCADE,
  exercise_id         TEXT NOT NULL REFERENCES exercise(id),
  position            INTEGER NOT NULL,     -- 在本次训练中的顺序
  rest_target_seconds INTEGER,              -- 本次采用的休息建议值
  note                TEXT
);

-- 一组（核心表）
CREATE TABLE set_entry (
  id                  TEXT PRIMARY KEY,
  session_exercise_id TEXT NOT NULL REFERENCES session_exercise(id) ON DELETE CASCADE,
  position            INTEGER NOT NULL,     -- 第几组
  weight              REAL NOT NULL,        -- kg
  reps                INTEGER NOT NULL,
  is_completed        INTEGER NOT NULL DEFAULT 0,
  rest_seconds        INTEGER,              -- 本组做完后休息了多久（NULL = 未记录/最后一组）
  rest_started_at     INTEGER,              -- 休息开始时间戳；崩溃恢复的依据
  completed_at        INTEGER
);

-- 设置（键值对）与 schema 版本
CREATE TABLE app_setting (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
```

### 6.2 关键字段说明

- **`rest_seconds` 存在「本组做完之后」那一段休息上**。第 3 组做完、第 4 组开始前的休息，存在第 3 组上。这样「开始下一组」这个动作只需写一条记录。
- **`rest_started_at` 是崩溃恢复的关键**。如果 App 在休息期间被杀，重开时用「当前时间 − rest_started_at」仍能算出真实休息时长。
- **计时用时间戳，不用计数器**。哪怕 App 被系统挂起十分钟，算出来的休息时长依然准确。这是不可妥协的实现约束。

### 6.3 关系

```
session ──< session_exercise ──< set_entry
                   │
                   └──> exercise（动作库）
```


## 8. 休息建议算法

### 8.1 设计约束

用户明确选择「全自动推算，不增加任何输入」（不采用 RPE 手动评分）。理由是 RPE 在健身房里十有八九会懒得填，填几天就荒废，不如让程序在后台观察。

### 8.2 输入

某个动作的最近 N 次训练记录（N 默认 3），每次包含该动作的所有组：重量、次数、顺序、组后休息时长。

### 8.3 计算步骤

1. **实际平均休息** `avg_rest` = 最近 N 次训练中，该动作所有非空 `rest_seconds` 的算术平均值。样本为 0 时直接走第 5 条。

2. **表现衰减** `decay`（对最近 N 次中的每一次分别计算）：
   - 取该次训练中该动作的组序列（按 `position` 排序），只取 `is_completed = 1` 的组
   - 设组数为 `n`，前半 = 前 `k` 组，后半 = 后 `k` 组，其中 `k = floor(n / 2)`
   - `decay = mean(前半的次数) − mean(后半的次数)`
   - **若 `n < 4`（`k < 2`），该次不参与衰减判定**，视为数据不足

3. **汇总判定**：`decay_final` = 参与判定的各次训练 `decay` 的平均值。若没有任何一次参与判定，判定为「保持」。

4. **判定与建议**：

   | 条件 | 结论 | 新建议值 |
   |---|---|---|
   | `decay_final ≥ 1` 且 `avg_rest < 当前建议值` | 休息不足 | `avg_rest × 1.25`，向上取整到 15 秒的倍数 |
   | `decay_final ≤ 0` 且 `avg_rest > 当前建议值 × 1.15` | 休息过长 | `avg_rest × 0.85`，向下取整到 15 秒的倍数 |
   | 其余 | 保持 | 沿用当前建议值 |

   其中「当前建议值」= 上次给该动作建议的值；从未给过建议时，取第 5 条的通用参考值。

5. **上下限钳制**：最终建议值限制在 **60 秒 ~ 300 秒**之间。

6. **无历史时的通用参考**：
   - 复合动作（深蹲、卧推、硬拉等）：150 秒
   - 孤立动作（弯举、侧平举等）：90 秒
   - 动作归属哪一类，由动作库预置数据里的 `muscle_group` / `equipment` 决定；自定义动作默认按孤立动作处理

### 8.4 证据必须可读

每条建议必须生成一句人能看懂的理由，例如：

- 「末两组次数 5 → 3，休息偏短」
- 「末组重量下滑 10kg」
- 「全程 10 次稳定，节奏合适」

**这是硬性要求**，不是锦上添花。

### 8.5 建议的生效方式（v1）

- 建议**只做展示，不做强制**，不阻断任何操作
- 训练总结页列出每个动作的建议
- 下次练同一动作时，休息计时界面显示一行小字「建议休息 120 秒」作为参考
- **v1 不做「到点提醒」，也不做「永久忽略」** —— 用户自己决定听不听

## 9. 可靠性与错误处理

| 风险 | 对策 |
|---|---|
| 训练中被系统杀进程 / 手机没电 | **每完成一组立刻写数据库**，不等训练结束。重开 App 自动回到未结束的训练 |
| 锁屏 / 切后台导致计时不准 | 计时基于 `rest_started_at` **时间戳**，用 `now − start` 计算，不依赖 `setInterval` 累加 |
| 数据库版本升级出错 | 版本化迁移，启动时自检，失败则回滚并保留原库 |
| 导入的备份文件损坏 | **先完整校验再写入**，校验不通过就拒绝，绝不破坏已有数据 |
| 导出失败 | 明确告知失败原因，不静默吞掉 |
| 训练中误触「结束训练」 | 二次确认；已记录的数据无论如何都保留 |

## 10. 测试策略

### 10.1 单元测试（重点）

针对 `src/domain/` 中的纯逻辑，这些是「算错了也不会立刻被发现」的地方：

- 容量计算（重量 × 次数求和）
- 1RM 估算（采用 Epley 公式）
- **休息建议算法** —— 各分支、边界值、上下限钳制、无历史数据的情况
- 导入 JSON 的校验逻辑：缺字段、类型错误、未来版本号、损坏文件

### 10.2 集成测试

数据库层用内存 SQLite 验证增删改查、级联删除、迁移。

### 10.3 手动测试

界面与真机手感由用户在手机上验证。开发过程中界面画面不可见，这是本技术方案的已知代价（见 §4.3）。

**M2 是关键节点**：不需要等全部做完，第二步之后就能拿去用真实训练来检验。后面的 M3–M6 也才有真实数据可看。

## 12. 开放问题（实施时再定）

1. **预置动作库的具体内容** —— 目标约 100 个常见动作，按肌群分组，手工整理。用户冷门动作可自定义（几秒的事）。
2. **1RM 估算公式** —— 暂定 Epley：`1RM = w × (1 + reps/30)`，仅用于趋势展示。
3. **「进步」页的默认排序** —— 暂定重量曲线与总容量曲线为主，1RM 次之。
4. **深色模式** —— 健身房环境下可能有用，v1 可跟随系统。

## 13. 附：本次设计中被否决的关键决策记录

| 决策点 | 选择 | 被否决项与原因 |
|---|---|---|
| 技术栈 | Expo / React Native | PWA 计时不可靠且迁移会丢数据；原生 Android 环境成本过高 |
| 数据存储 | 纯本地 + 留同步接缝 | 直接上云同步会让工作量翻倍，且尚未验证产品价值 |
| 记录界面 | 聚焦当前组（B） | 全览列表点击目标小；列表 + 操作条空间紧张 |
| 休息计时 | **正计时** | 倒计时会催促用户，且数据是"规定"出来的而非"观察"出来的 |
| 训练质量衡量 | **全自动推算** | RPE 手动评分与"越快越好"冲突，实际会被荒废 |
| 饮食热量 | 不做 | 会吞掉整个项目 |
| 训练模板 | 推迟到 v1.5 | v1 的"沿用上次组数 + 预填上次重量"已覆盖大部分便利性 |
