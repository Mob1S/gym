## 3. 信息结构

### 3.1 「进步」tab = 动作列表（已确认）

```
进步
┌────────────────────────────────────┐
│ 深蹲          9月16日 · 60 kg × 8  │  ╱╲╱   ← 迷你走势
│ 卧推          9月16日 · 40 kg × 10 │  ╲╱╲
│ 硬拉          9月2日  · 80 kg × 5  │  ╱╱
└────────────────────────────────────┘
```

- **只列练过的动作**（有已完成组、且属于已结束的训练）。没练过的动作不该出现在「进步」里。
- **按最近练过的排前面** —— 刚练完的动作一定在最上面，不用找。
- 行上的「60 kg × 8」= **最近一次训练里最重的那一组**（并列时取次数多的那组）。
- 迷你走势用**最大重量**这条线。理由：它每次训练都有值，不会空；而估算 1RM 会因为「整场次数都 > 10」而缺点（见 §4.3）。
- 空态：一个动作都没有 → 「还没有训练记录 / 去『训练』标签开始第一次吧」（与历史页同一套措辞）。

### 3.2 动作详情页 = 横向分页三张卡（已确认）

```
‹ 深蹲
┌────────────────────────────────────┐
│ 估算 1RM          最好 · 9月9日    │
│ 79 kg                              │
│ 估算 · 仅供参考 · 来自 60 kg × 10  │
│                                    │
│        ╱‾‾╲                        │   ← 占满屏的大折线图
│   ╱‾‾‾╯    ╲___                    │
│  9/2   9/9   9/16   9/21           │
└────────────────────────────────────┘
        ●   ○   ○                      ← 当前是哪一张
```

- 三张卡**横向分页**，一次一整张占满屏，左右滑动切换。
- 选它而不是竖排三张的原因：竖排时第三张会被挤到屏幕外，而「重量在涨、容量在掉」这种对比恰好需要两张同屏 —— 分页至少让每张图都有足够高度把刻度标清楚。
- **分页必须有可见的页码指示**（底部三个圆点），否则用户不知道旁边还有两张 —— 这是这个方案唯一的风险点，实施时不能省。

### 3.3 三张卡的措辞（刻意不同）

| 卡片 | 头上的字 | 大数字 | 图上的一个点 |
|---|---|---|---|
| 最大重量 | `最好 · 日期` | 该动作历史最大重量 | 那一次训练里最重的一组 |
| 估算 1RM | `最好 · 日期` + **`估算 · 仅供参考`** + 来自哪一组 | 历史最高的 e1RM | 那一次里所有可换算组里最好的一个 |
| 总容量 | **`最高 · 日期`** | 历史最高的单场容量负荷 | 那一次所有已完成组的 `Σ(重量 × 次数)` |

总容量**不写「个人最好」** —— 容量是训练量，不是力量成绩，一个练得少但更重的日子容量反而更低。三张卡的措辞本来就不该一样，这是 §5.4「区分口径与估算」的直接要求。

## 4. 指标口径

### 4.1 沿用 §5.4，一个字不改

- 容量负荷 = `Σ(weight × reps)`，只累加 `is_completed = 1` 的组；界面上叫**「总容量（重量 × 次数）」**
- e1RM = Epley / Brzycki / Lombardi 三个公式的算术平均；**公式不得更改**（换了会让曲线出现无解释的断层）
- e1RM 只在 `2 ≤ r ≤ 10` 计算；`r = 1` 直接返回 `w`；`r > 10` 返回 null 且**界面必须不显示**
- e1RM 出现的任何位置都必须带「估算 · 仅供参考」

### 4.2 「一次训练 = 一个点」

这是本次新增的关键约定。真实数据里**每一组的次数都不一样**（例如 `55×10 / 60×10 / 65×5 / 70×3`），所以：

> 同一次训练里每一组各算各的，然后**取最好的那个**当作这一场的点。
> 不按组画点 —— 那样一天之内会来回锯齿，看不出「进步」。

三个指标各自的「最好」：

| 指标 | 该次训练内的取值 |
|---|---|
| 最大重量 | 最重的一组（**不论次数**） |
| 总容量 | 所有已完成组求和，不分「最好」 |
| 估算 1RM | 能算出 e1RM 的那些组里最大的一个 |

### 4.3 次数 > 10 时会缺点，这是必须承受的

> 如果**某一次训练里所有组的次数都 > 10**，那一次在 e1RM 曲线上**没有点**。

处理方式（三选一是刻意的）：

- **不补 0** —— 0 是「练得很差」，而事实是「这一场不适合换算」，两者完全不同
- **不补估算** —— 外推严重失真，正是 §5.4 禁止的
- **线直接连过去**，但图下写一句「有 N 次训练没有可用于换算的组（次数 > 10）」，让用户知道曲线为什么少几个点

「最大重量」与「总容量」两条线**永远不会有缺点**（每组都参与），所以三张卡里只有 e1RM 需要这句说明。

### 4.4 「最好」= 历史最好

不设「最近 90 天」之类的时间窗。用户当前数据量还小，加窗口只会让他以为自己退步了。将来数据多了再加，那时曲线也才撑得起窗口。

## 5. 数据与分层

遵守 §7.2 的硬性约束：`app/` 与 `components/` 不 import `src/db/`，SQL 只出现在 `src/repositories/`，纯逻辑只出现在 `src/domain/`（可单测）。

### 5.1 新增 `src/repositories/progressRepo.ts`

```ts
export interface CompletedSetPoint {
  exerciseId: string;
  sessionId: string;
  startedAt: number;
  weight: number;
  reps: number;
}

/** 取已完成组的原始点。传 exerciseId 只取该动作，不传取全部练过的动作 */
export async function listCompletedSetPoints(
  exec: SqlExecutor,
  exerciseId?: string,
): Promise<CompletedSetPoint[]>;

export interface TrainedExercise {
  exerciseId: string;
  name: string;
  lastTrainedAt: number;
}

/** 「进步」页首屏的动作列表，按最近练过倒序 */
export async function listTrainedExercises(
  exec: SqlExecutor,
): Promise<TrainedExercise[]>;
```

两个函数都只统计 **`is_completed = 1` 且 `s.finished_at IS NOT NULL`** 的组 —— 进行中的训练不进「进步」，那和「进步」页只看已结束训练的历史约定一致。

**一个查询取回全部，而不是对每个动作查一次**：首屏要画每个动作的迷你走势，就需要每个动作的完整序列；对 20 个动作查 20 次是 N+1 —— `sessionRepo.listSessionSummaries` 的注释里已经写明「N+1 查询在手机上会肉眼可见地卡」，这里是同一条道理。这也正是 `listCompletedSetPoints` 的 `exerciseId` 做成可选参数的原因：首屏不传（一次全取、在 JS 里分组），详情页传（只要一个动作）。**一份 SQL，两个调用方，不复制。**

`ORDER BY s.started_at ASC, s.rowid ASC, st.position ASC` —— `rowid` 兜底不能省，理由与 `listSessionSummaries` 相同（同毫秒的两场训练时间戳完全并列，只按时间戳排会退化成扫描顺序）。

### 5.2 新增 `src/domain/progress.ts`（纯函数，全部可单测）

```ts
export interface ProgressPoint {
  sessionId: string;
  startedAt: number;
  maxWeight: number;
  volumeLoad: number;
  /** null = 这一场没有可用于换算的组（次数全 > 10） */
  bestOneRepMax: number | null;
  /** 上面那个值来自哪一组，用来在卡上写「来自 60 kg × 10」 */
  bestOneRepMaxSet: { weight: number; reps: number } | null;
}

/** 把某个动作的原始组，按训练分组折算成曲线上的点（按时间升序） */
export function buildProgressPoints(rows: CompletedSetPoint[]): ProgressPoint[];

export interface BestMark<T> { value: T; at: number }
export interface ProgressSummary {
  maxWeight: BestMark<number> | null;
  bestOneRepMax: (BestMark<number> & { from: { weight: number; reps: number } }) | null;
  maxVolumeLoad: BestMark<number> | null;
  /** 有几场训练算不出 e1RM，用来写那句说明 */
  missingOneRepMaxCount: number;
}

/** 三张卡头上的数字 */
export function summarizeProgress(points: ProgressPoint[]): ProgressSummary;
```

e1RM 的公式**不在这里重写**，一律调用 `metrics.ts` 的 `estimateOneRepMax` —— 公式只能有一份实现，这是 §5.4「公式一旦确定不得更改」在代码上的落实方式。

### 5.3 新增 `src/components/TrendChart.tsx`

一个组件同时承担详情页的大图和列表行的迷你走势：核心都是「一条折线 + 每个点一个圆点 + 高亮最好那一次」。

```ts
interface TrendChartProps {
  /**
   * 每个下标对应一次训练。`null` = 那一次没有可画的点（e1RM 曲线上
   * 「整场次数都 > 10」的训练就是这种）—— 线从两侧直接连过去，不补 0、不补估算。
   */
  values: (number | null)[];
  /** 高亮的下标（最好那一次）；null 表示不高亮 */
  highlightIndex?: number | null;
  /** true = 带横向刻度线与 x 轴标签（详情页）；false = 迷你走势 */
  showAxis?: boolean;
  height?: number;
}
```

- 用 `react-native-svg` 的 `Polyline` + `Circle` + `Line`，不引图表库：这里只有折线和圆点，引库反而要跟它的样式打架。
- **有效点只有一个时只画点、不画线**，并在卡外补一句「再练一次就能看到走势」。
- **一个有效点都没有时**：不渲染图，显示「还没有记录」。
- 点为 `null` 的位置**不画圆点**；`highlightIndex` 指向的点画成绿色实心并标出数值与日期。

## 6. 测试

jest 的 `testMatch` 只收 `src/**/*.test.ts`，所以界面不写单测（与项目现状一致），靠 `tsc` + 真机验收。

**`src/domain/progress.test.ts`（重点）**

- `buildProgressPoints`：同一个动作多次训练 → 点的顺序按时间升序；每次训练只出一个点（不是每组一个点）
- 一次训练里三个指标各自取值正确：`55×10 / 60×10 / 65×5` 这一场，最大重量 = 65、容量 = `550+600+325`、最佳 e1RM 来自 `60×10`
- **`60×10` 的 e1RM 高于 `70×3` 的 e1RM** —— 用真实数字锁住「最佳 e1RM 不一定来自最大重量那一组」这条容易搞错的语义
- 整场次数都 > 10 → 该点 `bestOneRepMax` 为 `null`，且不参与「最好」的评选
- `summarizeProgress`：三个最好值各自的日期正确；`missingOneRepMaxCount` 数得对
- 空输入 → 全是 null、计数为 0，不抛异常

**`src/repositories/progressRepo.test.ts`**

- 只统计 `is_completed = 1` 的组（未完成的占位组不算）
- **进行中的训练不算**（`finished_at IS NULL` 的整场排除）
- 只统计该动作的组（同一场里别的动作不算）
- 不传 `exerciseId` 时返回全部练过的动作
- `listTrainedExercises`：按最近练过倒序；没练过的动作不出现

## 7. 真机验收

| # | 步骤 | 期望 |
|---|---|---|
| 1 | 练一场（做几个不同次数与重量的组）→ 保存 → 进「进步」 | 那个动作出现在列表最上面，行上是「最近一次日期 · 最重的一组」，右边有迷你走势 |

## 9. 风险

| 风险 | 应对 |
|---|---|
| `react-native-svg` 是原生模块，本地跑不起来就没法在真机上验证 | 与 M5 的真机验收、以及已排队的重新打包合并成一次云构建 |
| 横向分页没有可见提示 = 用户不知道旁边还有两张 | 底部圆点指示是**必做项**，不是可选项；真机验收第 2 条专门验它 |
| 每次训练一个点，数据少时曲线只有两三个点，看起来不像「曲线」 | 明确接受：真话比好看的图重要。空态与稀疏态都有专门文案 |
| 图表的 Y 轴范围：容量与 e1RM 的绝对值差一个数量级 | 三张卡各有各的 Y 轴，不共用一个刻度 |
